Connectivity
Communication Options for the CS/EEE Bioreactor Challenge
The bioreactor project consists of several subsystems that are managed and 
coordinated locally by a microcontroller. In addition their behaviour should be 
able to be monitored and controlled remotely by some kind of dashboard or 
user interface.
In fact, coordination and communication will be performed using at least two 
different microcontroller boards.

The Arduino Nano ESP32 is a development board in the popular Arduino Nano 
format, employing the ESP32-S3 microcontroller (more recent than the ESP32s

Communications between the microcontrollers are digital and require more 
complex structure — protocols — to get the information across.
UART
Universal Asynchronous Receiver Transmitter
A common — even ubiquitous — approach to passing digital signals over wires 
is asynchronous serial or UART. (Strictly, UART refers to the device 
implementing the protocol rather than the protocol itself, but the terminology 
gets used pretty loosely.)

A crucial feature here is that the communications are asynchronous — meaning 
there is no shared signal keeping the two sides in step with one another, each is

It’s a digital signal, which means the information is carried by the voltage on the 
wire being in one of two states — which might be called high/low, on/off, true/
false, 0/1 etc. Usually low is at ground level and high is above some positive 
threshold, but the details may vary from device to device. Since the voltage can 
only be at one level at a time and there are only two recognised levels, only a 
single bit of data can be conveyed at a time, so data must be passed serially, 
bit by bit.

Data is organised into this parade of voltage changes in packets, each 
containing a little chunk of data. The exact structure is configurable, but a 
packet always begins with a single start bit, alerting the receiver that data is 
incoming. There is then a sequence of 5-9 data bits (the number can vary 
between devices but is fixed for a particular connection and must be specified 
externally). There can then be an optional parity bit, which provides for a simple 
form of error checking, but this is rarely used. Finally 1 or 2 stop bits declare 
the packet done.

The most common configuration uses 8 data bits, no parity and 1 stop bit, 
abbreviated as 8N1. Note that the frame bits mean that it takes 10 bits of signal 
to transfer each byte of data.

Synchronous Communications
CLOCK SIGNAL
The alternative to asynchronous communication is synchronous 
communication, where there is some shared timing signal to keep both parties 
in step. This is typically in the form of a simple pulse train or square wave 
(though probably not quite as perfect as depicted here).

Each cycle of the waveform includes a rising edge and a falling edge. The exact 
cueing from these may vary between devices and configurations, but typically 
the sender and receiver will synchronise to different edges. This provides a 
margin for error in the synchronisation and reduces susceptibility to timing 
inconsistencies
SPI
Serial Peripheral Interface
One common synchronous serial communication protocol is SPI.

This uses four wires to manage communication between devices performing 
two different roles. A controller provides the clock signal and controls the 
process, while a peripheral sends and receives data on cue. There are 
dedicated data lines in each direction, labelled in terms of the two roles: 
peripheral-in/controller-out (PICO) and peripheral-out/controller-in (POCI). PICO 
connects to PICO on both devices and POCI to POCI, rather than having the 
TX-RX crossover we saw for UART. A fourth chip select (CS) line is used to tell 
the peripheral it’s the one being targeted.


--- PAGE 11 ---
A controller can talk to multiple peripherals independently on shared PICO & 
POCI lines, but each needs its own chip select line, and the wiring can get out 
of hand if there are many peripherals.
An alternative daisy chain configuration uses only a single CS line for all 
peripherals. In this case data flows from one device to the next. The controller 
must send and receive all its device packets together so that each reaches its 
destination, and must collect all responses similarly, so it can get a bit unwieldy.
#include <SPI.h>
https://docs.arduino.cc/learn/communication/spi
SPI functionality is provided to your Arduino code in the SPI library, which 
comes preinstalled with your boards but you do need to #include the 
appropriate header.

But note that although multiple controllers can share the bus, only one can be

Messages are organised by topic, simple text string descriptors that clients use 
to declare what they are publishing and/or what they want to subscribe to. The 
broker routes relevant topics to interested subscribers. Topics are hierarchical 
and wildcards are supported for subscribing.

MQTT communicates in packets with a variable structure. The smallest valid 
packet is 2 bytes, and while much larger packets are nominally supported they 
are rarely used. Most MQTT packets are very lightweight, which is one of the 
things that makes it popular for resource-constrained IoT applications.
#include <PicoMQTT.h>
https://github.com/mlesniew/PicoMQTT
MQTT support is not installed for your boards by default, but there are many 
implementations available. We recommend PicoMQTT, which you can install via 
the Arduino IDE’s Library Manager, but if you’re familiar with something else 
then feel free to use that instead.
PicoMQTT can run a broker as well as a client, so one possible way to organise 
your connectivity would be to use one ESP32 to run the broker that the client 
ESP32 talks to. But note that eduroam won’t allow you to run a server on it, so if 
you take this approach the broker will need to be on some other network you 
can connect to.

The final piece of the puzzle is the user interface or dashboard that you will use 
to monitor and control your bioreactor remotely. You are free to do this in any 
way you please, short of getting someone else to do it for you. No specific 
software development tools, coding environment or technology are prescribed, 
you can use whatever you are comfortable with as long as the basic 
requirements are met: ie, that the interface allows you to monitor the bioreactor 
parameters over time and set target values for temperature, pH and stirring 
speed. There are a few weak suggestions on the following slides, but you are 
welcome to ignore them and do something else entirely.
https://nodered.org
Node-RED is a “low code” web-based environment that allows you to 
graphically build web applications that receive, process and display data from 
disparate sources, known as “flows”. The popular FlowFuse Dashboard add-in 
(https://dashboard.flowfuse.com/getting-started.html) adds features to make it 
easy to build dashboards.


--- PAGE 20 ---
Various applications are available for iOS and Android to talk to IoT devices 
using MQTT, and these can be used to construct a control interface if you 
design your MQTT messaging appropriately.
https://thingsboard.io
Numerous web-based services exist to support connectivity and control 
amongst disparate IoT devices. One example is ThingsBoard, which offers a 
commercial service but is also open source and allows you to run your own 
server if you want. ThingsBoard is versatile and provides a lot of functionality 
but can be quite complex as a result.
If you’re feeling adventurous you could even build your own custom controller 
around something like the ESP32 LVGL TFT, popularly known as the Cheap 
Yellow Display, an ESP32 board with a built-in touch sensitive screen. 
Any of the above approaches is acceptable, as are many others. Show us what 
you can do!
