Idea 1: Trying Every Possible Move Sequence
Recursive Action Search (try all moves)
Following the Noughts and Crosses approach from Week 5,
a natural first idea is to branch on every legal action at every
row:
1 def try_all_moves(board):
2 best = float("-inf")
3 for action in ALL_FIVE_ACTIONS:
4 sandbox = board.clone()
5 landed = apply_step(sandbox, action)
6 if landed:
7 val = score_board(sandbox)
8 else:
9 val = try_all_moves(sandbox)
10 best = max(best, val)
11 return best
Correctness vs Efficiency
▶ Soundness: The recursion is logically
valid and visits every reachable trajectory
until the block lands.
▶ Redundancy: Thousands of distinct
left-right-skip sequences end at the exact
same landed placement.
Key Engineering Question
Before coding this search, how many recursive
calls does a single falling block require?

Complexity Analysis: Why Exhaustive Action Search Fails
Branching Factor and Depth (Weeks 3 &
5)
▶ Branching factor (b = 5): Rotate clockwise,
rotate anticlockwise, move left, move right, or
skip/fall.
▶ Search depth (d ≈ 20): The grid has 24 rows,
giving roughly 20 downward steps before landing.
The number of action sequences for one block grows as
bd ≈ 520 ≈ 9.5 × 1013,
and reaches 540 ≈ 9.1 × 1027 for a 2-block lookahead.
Action-Tree Explosion
d = 0
... (520 leaves at d = 20)
Intractable at Runtime
Unlike Noughts and Crosses (5,478 states), 520
states cannot be searched within human patience
or the 15-minute / 256 MB server limits.

Strategy 2: Target-State Search
Martin Benning (University College London) Assignment 4: Strategy and Implementation Hints 8 / 18

Idea 2: Focusing on Target Landing Positions
Shifting Perspective (Plan B)
Instead of searching every intermediate path,
enumerate only the distinct final configurations in
which the falling block can land:
▶ Horizontal column: 10 columns
(x ∈ {0, . . . , 9}).
▶ Orientation: At most 4 distinct rotations (O has
1; I, S, Z have 2; J, L, T have 4).
Reduced Search Space
Total candidates per block satisfy 10 × 4 = 40 states,
which executes in milliseconds in Python.
Search Space Comparison
Search Strategy States / Piece Feasible?
Exhaustive action tree ≈ 520 No
1-piece target states ⩽ 40 Yes (fast)
2-piece lookahead ⩽ 1,600 Yes
New Subproblem
For each target (rotations, target x), generate
one clean action sequence that steers the block there
and drops it.

Moving Towards Target: Rotation Order and Wall Boundaries
Does Order of Operations Matter?
Every call to rotate() or move() also drops the block by
one row. Should we translate horizontally first or rotate
first?
Wall Kick-Back and Obstructions
In board.py, rotating a wide piece (Shape.I) at a wall
shifts it inward to stay in 0 ⩽ x < 10, while rotating into
blocks cancels the rotation:
▶ Moving to target x before rotating can push the
block out of target x.
▶ Rotating first in open space, then aligning
falling.left to target x, avoids wall shifts.

Designing the Heuristic Score Function
Core Structural Features
▶ Score Gain
(∆S = sandbox.score - board.score): Captures
immediate 1–4 row clear points (25 to 1,600), as
land block() clears full lines automatically.
▶ Height (H): Aggregate or maximum column height
(taller stacks risk top-out collision at y = 0).
▶ Buried Holes (K): Empty cells trapped beneath at
least one landed block in the same column.
▶ Bumpiness (B) & Cells (Ncells): Penalise adjacent
height jumps P x |hx − hx+1| and remaining blocks.

Three Key Sets on board
1. board.cells: Landed (x, y) set (O(1)
lookup).
2. board.falling.cells: Active block
cells (plus .shape, .left).
3. board.next.cells: Upcoming block
cells (for 2-piece lookahead).
Unordered Iteration
Python sets have no fixed order; scan x and y
with range() in O(W · H) time.

Coordinate Conventions and Simulation Safeguards
Top-Left Coordinate Grid
▶ Origin (0, 0): Top-left corner.
▶ Columns (x): 0 (left) to 9 (right).
▶ Rows (y): 0 (top) to 23 (bottom floor).
▶ Column height: For topmost occupied row
ymin, height is 24 − ymin.
Tracking Rotations Cleanly
Count how many clockwise rotations (0–3) your
simulation loop applies from spawn rather than
inferring orientation from cell coordinates.
Ensuring Safe Landing in sandbox
1. Return Booleans: rotate() and move() return
True if the 1-row step landed the block early.
2. Conditional Drop: Once at target x, call
move(Direction.Drop) only if not landed.
3. Block Promotion: Landing moves sandbox.next
into sandbox.falling; moving after both land
raises NoBlockException.

Summary of Strategies and Implementation Roadmap
Algorithmic Choice
▶ Strategy 1 (Exhaustive Action Tree):
Exploring all move sequences (≈ 520 paths) is
computationally intractable.
▶ Strategy 2 (Target Landing States):
Enumerating final (rotation, column)
placements (⩽ 40 states, or ⩽ 1,600 with
2-piece lookahead) is fast and effective.
Implementation Requirements
1. Sandbox Cloning: Clone board.clone()
independently for every candidate target.
2. Steer & Drop: Rotate early in open space, align
falling.left to target x, guard early
landings, and issue Direction.Drop.
3. Heuristic Scoring: Combine score gain ∆S,
column heights, buried holes, and bumpiness
from sandbox.cells.
Keep the search space small, guard edge cases, and tune weights systematically.
